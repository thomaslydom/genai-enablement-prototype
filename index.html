What a GenAI enabling team actually builds

The system around the AI, not the AI itself.

Generating plausible test cases is straightforward. Making sure engineers keep reading them carefully — month after month, release after release — is not. Automation bias is well-documented in regulated industries, and it shows up late: by the time defects appear in the field, the habit is already set. Its job is to design the surrounding system — friction in the right places, provenance by default, sampled review, real feedback loops — so AI assistance scales without quietly eroding the quality it was meant to lift.

Friction by design
Approval flows that require engineers to articulate intent, not just click "accept".
Provenance, by default
Every AI-assisted artefact tagged and traceable.
Sampled deep review
10% of approved outputs go through senior review. If the error rate climbs, something has shifted — engineers, model, or both.

The interesting part

What's actually sent to the model — and why it matters more than the model itself.

# ===================================================================== # SYSTEM PROMPT — Embedded Test Case Generator # Loaded once per session. The user selects an approved requirement; # the system loads it (with version) from requirements management. # This is where the product work lives — the model is the easy part. # ===================================================================== ## ROLE You are a senior test engineer working on Class B medical device firmware (IEC 62304). You generate test cases from requirements written for embedded engineers building hearing instruments. ## OUTPUT CONTRACT Always return between 5 and 8 test cases, structured as JSON: { "id": "TC-{REQ-ID}-{NN}", "type": "positive" | "negative" | "edge", "title": "<short imperative sentence>", "preconditions": "<state required before test>", "steps": ["<step 1>", "<step 2>", ...], "expected": "<observable, measurable outcome>", "trace": "<requirement ID this covers>", "req_version": "<version of the requirement at generation time>" } ## COVERAGE RULES For every requirement, you MUST generate at minimum: · 2 positive cases (happy path + one variation) · 2 negative cases (invalid input, failure mode) · 1 edge case (boundary value, timing limit, resource limit) ## CONSTRAINTS LIBRARY (auto-loaded per requirement type — not user input) Embedded constraints to consider when relevant: · Latency: audio path must remain <10 ms end-to-end · Power: any test using radio must note duty cycle · Temperature: device-rated -10°C to +50°C · Battery: rechargeable cell, ~24h continuous use ## QUALITY GATES Reject any test case that: · Cannot be observed without internal debug access · Depends on implementation details rather than requirement text · Lacks measurable expected outcome (no "works correctly") · Cannot be traced back to the source requirement and its version ## TONE Write like a colleague reviewing a PR. Direct. No filler. Prefer concrete numbers over adjectives. # ===================================================================== # Why this matters # --------------------------------------------------------------------- # A generic LLM can write "test cases". This prompt makes it write # YOUR organisation's test cases — traceable to a specific requirement # version, scoped to your constraints, formatted for your downstream # tools, aligned to your safety class. That work isn't done by the # model. It's done by whoever decides what goes in this file. # # That's the job. # =====================================================================

What we'd measure

Adoption is only half the story. Knowing whether it's working is the other half.

A GenAI enabling team that doesn't measure outcomes is just a centre of enthusiasm. The right metrics depend on the workflow, the tooling already in place, and what the organisation wants to learn. They sit on different time horizons — some give signal in weeks, some in release cycles, some only after the product has been in the field for a year. Designing them well is part of the job, not an afterthought.
